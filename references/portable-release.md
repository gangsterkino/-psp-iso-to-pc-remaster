# 从已验证构建到便携发布包

此阶段输入是当前版本的 EXE、资源、运行库、源码与验证记录。输出是一个新的本地 ZIP、外置 SHA-256 清单和验证报告。创建本地可分发文件不包含上传、公开发布或向别人发送；这些动作需要用户明确提出。运行库的开源许可不自动覆盖游戏、汉化、音乐或高清素材的再分发权；按项目已确认的资源使用范围选择完整包、补丁包或用户本地生成包。

## 1. 先固定版本和功能，不用旧程序冒充原画质精简版

记录版本、目标架构、代码提交或源码快照哈希、资源清单、已完成检查和未测项目。保留旧 ZIP、旧 EXE、原素材及存档，新的变体使用新的输出名和暂存目录。

| 变体 | 程序与修复 | 资源设置 | 必须重新验证 |
|---|---|---|---|
| 原画质精简版 | 使用当前修复版，保留鼠标、AUTO/SKIP、渲染及存档修复 | 禁用高清替换并移除已证明非必需的高清素材 | 无高清目录也能启动；原字库、UI、剧情与输入路径可用 |
| 高清版 | 当前修复版及匹配的高清加载器 | 完整已验收高清资源 | 字库、动态表情、接缝、场景及资源匹配 |
| 高清无损精简版 | 支持对应编解码格式的当前程序 | ISO 去重 + 经生产解码器验证的无损图片 | 所有像素与配置相等；加载时延；ISO 兼容性 |

不要退回早期“支持鼠标”的 EXE 来减少画质：早期程序可能重新带回黑屏、字库、接缝和输入缺陷。关闭高清的开关也不保证所有高清文件都可删；检查启动必需项、默认字库、UI 配置及回退路径。记录真实测量后的压缩包大小、解压文件总量和首次运行额外空间，统一注明 GB 是十进制还是 GiB。

## 2. ISO 与解包副本去重：先建立运行时能力，再移除副本

ISO 和 `disc/PSP_GAME/…` 可能内容重复，但游戏可能同时按文件名和原始扇区访问数据。仅查看目录、能进入标题，或“解压文件都在 ISO 里”，都不足以证明可删除任一份。

选择明确的资源模式；优先让文件路径与扇区读取都访问同一个只读 ISO。具体环境变量和接口按实际引擎实现，不能把本项目的 `REFRACT_DISC_MODE=iso` 当作所有项目的现成功能。

删除**新发布暂存目录中的解包副本之前**，必须满足以下门槛：

1. 运行时有可验证的 ISO9660 索引与文件视图：路径大小写/规范化、独立文件游标、边界与 EOF、空文件、同步/异步 read/seek、目录遍历、stat/chdir 和实际使用的模块元数据接口。ISO 写入必须拒绝；存档仍走独立可写路径。
2. 原始 LBN/扇区访问及整盘读取保留；不能用“文件长度正确”替代扇区语义测试。确认扇区映射的来源、单位及边界，不随意丢弃运行时仍依赖的 sector-map 文件。
3. 通过**实际生产运行时/HLE 接口**读取提供的 ISO 中全部普通文件，与原解包副本逐字节或 SHA-256 比较；比较独立游标、跨边界、EOF、无效路径、截断镜像和越界扇区。另做原解包模式回归。
4. 新模式在独立干净运行目录完成已约定的真实启动、剧情、音频、场景切换和存读档检查；若用户保留手测权，明确标为待用户验证，不操作其窗口。此时可以交付明确标注“待实机验收”的候选包，不能宣称完整兼容。
5. 去重仅修改新 stage：保留源 ISO、源解包树和旧包作为回退。清单断言最终模式只保留约定的一份资源，例如恰好一个 ISO、零个解包 `PSP_GAME` 数据副本。

减小下载体积的顺序通常是资源去重、纹理无损存储、移除已证实非运行必需的构建内容，最后才比较外层 ZIP 压缩级别。不要未经要求减少分辨率、裁剪语音/剧情、转有损或删除未理解的数据文件。

## 3. 创建从未运行过的发布 stage

通过明确的复制清单组装新目录；不要将整个开发工程直接打包。清单至少列出当前 EXE、生成的 BIN、资源模式必需文件、对应 DLL、启动器、用户说明、第三方许可与对应源码。每个来源文件与复制品核对长度、SHA-256。

- stage 内不得有 `userdata`、`.refract`、`logs`、`captures`，包括空目录；运行时首次启动再创建。
- 排除编译产物目录、工具链、缓存、版本库、凭据和个人存档。必要源码可以单独制作 `SOURCE.zip`；制作时同样用显式清单并独立检查其内容，不能把隐私数据藏进内层 ZIP。下面的 helper 不递归审核内层压缩包。
- stage 不接受符号链接或 Windows junction/reparse point；所有资源都是清单中真实文件。
- 停止会写入 stage 的转换器、编辑器、同步程序；不要在打包时更新它。helper 在开始、写入过程和结束检查内容变化，但它不是文件系统快照工具。
- smoke test 必须从另一个新解压目录运行。被游戏创建过存档/日志的目录不得再当作干净发布 stage。

## 4. 启动器与依赖闭包

Windows CMD 启动器应 `setlocal`，再 `cd /d "%~dp0"`，所有参数和路径加引号。仅在子进程环境中清除该运行时自己的旧环境变量，随后将只读资源、纹理包、存档、截图和日志都绑定到包内相对位置。不修改系统环境，也不引用制作者电脑的绝对路径。

启动前检查该模式真正需要的 EXE/BIN/DLL/ISO/配置；创建自己的 `userdata`、`logs`、`captures`。每个变体有自己的首次运行存档目录；迁移存档需要用户明确选择且关闭写入进程。不从开发测试目录复制存档作为“开箱可玩”的捷径。

从 EXE 开始递归检查非系统 DLL 导入，确认打包架构与依赖架构一致；静态依赖也需记录版本、构建方式和许可。不要依赖开发机 PATH 才能找到 DLL。无损 PNG/WebP 的新加载器要与 EXE 同步，不能仅替换资源后继续使用旧程序。

用被打包的源码快照和配置说明对应此 EXE，包含修改补丁、实际使用的第三方源码/通知，以及许可证所要求的源码或其他履行材料。只记录已完成的对应关系；“放了一个 LICENSE”不代表所有依赖和资源都已覆盖。

用户说明应写明目标平台、完整解压后双击的文件、操作方法、存档位置、已知限制、当前版本与必要硬盘空间。截图或视觉方案若非运行中画面，应明确区分。不要将未实现的视频、未测剧情、未测系统兼容性写成已支持。

## 5. 使用附带 helper 生成与核验 ZIP

`scripts/portable_archive.py` 仅用 Python 标准库；不运行游戏、不解压 ZIP、不删源资源、不上传。ZIP 内顶层目录取 stage 名。默认 ZIP_DEFLATED 压缩级别 6，可显式指定 0–9；已压缩图片通常无需一味提高外层级别。

```powershell
python "<skill-root>/scripts/portable_archive.py" build `
  --stage "D:/project/work/release-stage/Game-HD-v1" `
  --archive "D:/project/outputs/Game-HD-v1-Windows-x64.zip" `
  --manifest "D:/project/outputs/Game-HD-v1-manifest.json" `
  --compression-level 6

python "<skill-root>/scripts/portable_archive.py" verify `
  --archive "D:/project/outputs/Game-HD-v1-Windows-x64.zip" `
  --manifest "D:/project/outputs/Game-HD-v1-manifest.json" `
  --report "D:/project/outputs/Game-HD-v1-verification.json"
```

`build` 拒绝覆盖已有 ZIP/manifest，拒绝把 ZIP 或 manifest 放进 stage，拒绝私有/开发目录、链接、路径穿越，以及 Windows 大小写或 Unicode 归一化后重名。它逐文件计算 SHA-256，写入临时 ZIP 时再次核对，完成后重新检查 stage，遍历整个 ZIP 检查路径、数量、长度、SHA-256 和完整 CRC，通过后将临时文件原子替换到独占预留的目标文件。ZIP 与 JSON 是两个独立文件，不能做到跨文件事务；进程被强制终止后应检查残留文件并使用新版本名重建。

外置 manifest 记录整个 ZIP 的 SHA-256/字节数和每个条目的 SHA-256/字节数，避免把“包含自身哈希的清单”写进包内。`verify` 要求条目集合**完全相等**，不会仅检查清单列出的子集；它拒绝重复条目、路径穿越和链接，完整读到 EOF 检查 CRC，再核对每个文件哈希。验证失败返回退出码 1，成功返回 0；可选报告也拒绝覆盖旧证据。SHA-256 清单用于完整性复核，不是对文件来源的数字签名。

helper 的目录阻止规则故意严格：需要交付的开发源码先按专用清单归入已审计 `SOURCE.zip`，不要为了让现有 stage 通过而随意关闭阻止规则。它没有理解游戏依赖的能力，不能证明缺少某个资源仍能运行。

## 6. 发布验收的证据层级

| 证据 | 可以说明什么 | 不能替代什么 |
|---|---|---|
| 编译通过、导入审计 | 构建成功，已检查依赖 | 干净环境中真实启动 |
| 清单/大小/SHA-256/全 CRC | 此 ZIP 和清单一致且可完整读取 | 游戏功能与画面正常 |
| 全纹理生产解码像素相等 | 存储变换无损 | 场景加载无卡顿 |
| 减少 PATH 后从独立目录启动 | 本次机器/目录内便携启动 | 另一台电脑或所有显卡兼容 |
| 真实剧情、输入、音频、存读档测试 | 被测路径在该环境可用 | 全剧情、通关稳定性 |

运行检查要覆盖空格与中文路径、从 stage 之外启动 CMD、缩减开发 PATH、首次存档、菜单、首个剧情场景、音频、鼠标、AUTO/SKIP、焦点切换、画质切换、截图和保存后重开等实际支持的功能。独立测试目录有独立存档，记录精确 EXE 路径和哈希。只操作已授权的测试窗口；用户正在玩的窗口保持由用户操作。发生用户输入冲突则停止窗口操作，并区分“退出原因不明”和“已证实崩溃”。

最终交付列出 ZIP、清单、验证报告、大小与节省量，明确已测/未测范围。报告中的 `runtime_test: not_performed` 是 helper 的固定事实，应另附真实运行测试记录，不能手工改成通过。用户拥有手测权时，静态打包检查做完即可交付候选结果，同时准确保留实机验证缺口。

## 本次案例的可复用结论

既有流程先将“ISO + 解包树”改成经过运行时文件/扇区测试的 ISO-only，再将原始 RGBA 改为 PNG，最后优先使用更小的无损 WebP 并保留更小的 PNG。最终包为 1,894,939,666 字节，解压文件为 2,089,249,194 字节，1,668 个条目；这些是一个特定项目的历史测量，不能套成别的游戏的预期体积。最终包的静态与像素检查通过，后续实际游戏窗口验收由用户进行。复用其证据门槛和版本隔离方式，不复制游戏特定地址、资源、构建参数或未经复核的功能承诺。
