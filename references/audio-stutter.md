# 语音断续：按通道验证音频排队与宿主回调

用于原生 PC 或 Android 工程中“语音断续而背景音乐连续”、偶发缺帧或音频退出卡住的诊断与修复。先复用现有素材与运行时，核对生产代码和实际提交节奏；本页不是重新编码语音、提高音量或替换解码器的默认理由。

## 1. 先把可复现条件与根因分开

记录平台、源码/二进制版本、采样率、宿主回调帧数、各 guest 通道每次提交帧数，以及断续发生的场景。通道参数可能在运行中改变，初始化值不能代表整个播放期。

ULJS00354 案例的自定义 PCM/ADPCM 混音路径采用 448 帧，静态调用关系倾向于对白路径，但未以真实游戏动态标签确认；三个流通道初始化为 256 帧，其中背景音乐等流路径会改为 1024 或 2048 帧。Windows 后端请求 44100 Hz、512 帧、四个后端缓冲。448/1024 的语音与背景音乐对照属于本案例模型，不能硬编码成其他游戏或设备的参数。

本轮诊断已区分以下事实：

| 假设或观察 | 生产源码与探针支持的结论 |
|---|---|
| 448 不能整除 512，所以语音必然断续 | 不成立；理想调度下实际 mixer 的这组输入没有缺帧。帧数不整除本身不是根因 |
| 阻塞提交先等旧音频耗尽才复制新块 | 当前源码已经先入队再等待；旧的 wait-before-copy 问题不能重复当作本轮根因 |
| guest 阻塞音频总是持有执行锁，阻止别的线程运行 | 当前阻塞 HLE 与 SAS 路径会释放 guest 执行令牌；必须检查实际路径再归因 |
| 全局 underrun 为零，所以语音完整 | 不成立；按所有通道最大消费帧数计算，会被完整的背景通道掩盖 |
| 短块在人工生产延迟下断续、长块连续 | 证明这种排队/调度条件足以产生相似症状；仍需真实游戏时间线才能确认用户现场的触发条件 |

优先记录每通道的提交/消费帧数、剩余队列与部分供给回调。将原本有数据但不足本次回调的通道，与从未播放、已停止或自然句尾的通道分开分析；不能仅把静音样本或一个累计计数视为故障。

## 2. 让短块在宿主消费前有足够余量

保留“复制新块入队，再决定是否阻塞”的顺序。修复点是阻塞生产者的唤醒水位与设备实际回调需求，而不是把所有游戏提交强行改成同一帧数。队列必须有上限，满队列行为、取消和非阻塞提交契约保持明确；不要靠丢样本、重采样或无界缓存掩盖断续。

本轮实现采用显式 `set_callback_frames` 配置宿主需求：

- 未配置时为 0，沿用原有 pacing，避免无后端的调用者被静默改成另一套时序。
- 设备配置后，blocking 唤醒水位为 `max(guest_block_frames, 1024, 2 × callback_frames)`；同一设备生命周期内的 callback quantum 只增不减，本实现上限为 2048 帧。1024 帧是本轮选择的最小排队余量，不是 PSP 或 Android 的固定要求。
- 对连续的顺序阻塞提交，瞬时队列最多为水位加一个 guest 提交块；这不是含并发或非阻塞写入时的通用容量上限。较大的 guest 块仍由自身块长约束，既有环形队列容量与写入边界检查继续有效。
- 增加逐通道 `partial_callbacks` 与 `missing_frames`：只有该通道 `available > 0` 且不足本次回调才计数，不把空闲通道算作持续 underrun。自然句尾也可能出现部分回调，完全空队列则不在该指标内，所以计数非零或为零都不能单独证明听感；需结合提交时间线解释。这是可查询的引擎诊断接口，不等于已接入用户日志。

这是有界预排队与延迟之间的取舍。小 callback 不保证生产者有充分运行时间：仅取 `max(448, 2 × 192)` 仍为 448，未增加短块余量；本轮因此同时设置最小水位。案例中 512 帧回调对应 1024 帧水位，44100 Hz 下约 23.2 ms；相对旧的 448 帧水位多 576 帧，约 13.1 ms。水位不是整条音频链的总延迟，还需计入后端缓冲和设备延迟。2048 帧 callback 配置对应 4096 帧水位，约 92.9 ms；若 guest 块更大，水位也可能更大，不能把 92.9 ms 称作通用延迟上限。

测试短句结束、跳过/切换对白、停止、清空和重新预约通道，确认额外队列不会保留上一句音频、无限等候更多数据或改变取消语义。调整水位应以可接受的延迟和测得的生产抖动为依据，不能把本案例的 1024 帧下限或两倍回调余量视为所有引擎的唯一正确值。

## 3. Android 生命周期与源码同步

Android 应根据实际配置和回调观测设置水位，不能直接复制 Windows 的 512 帧。`AAudioStream_getFramesPerDataCallback` 可能返回 `AAUDIO_UNSPECIFIED`，此时 `numFrames` 可在回调间变化；`framesPerBurst` 可作为启动时的参考，不能当作固定 callback 大小。依据见 [AAudio 音频 API](https://developer.android.com/ndk/reference/group/audio)。

重新打开 stream 后可能协商出不同设置，应重新查询参数、重建该 stream 的回调观测基线。本实现通过 `device_reset` 清队列并将 callback quantum 归零；普通通道重置保留当前设备配置。不要沿用旧设备的最大 callback 值作为永不下降的进程级常量。音频焦点丢失、Surface 消失或进入后台时，guest 调度与声音一起暂停；恢复时重新确认设备、回调参数与队列状态。[AAudio 断开与恢复指南](https://developer.android.com/ndk/guides/audio/aaudio/aaudio)也要求在错误回调之外的线程关闭 stream。

取消、断开或退出必须能唤醒阻塞生产者，即使设备不再提供回调。关闭与重开设备放在音频回调之外的线程；回收工作线程之后再释放 guest RAM。检查新增排队逻辑没有绕过既有停止标志、条件变量通知和生命周期路径，详见 [Android 宿主适配与生命周期](android-release.md)。

通用 AudioEngine、平台后端与头文件的变更应同步到当前 Windows 工程、Android 工程及可重新生成工程的运行时来源/模板；记录补丁或对应哈希。只改生成副本会在重新生成时丢失修复。平台特有的取消/设备恢复代码仍按各自职责保留，不为追求文件相同而覆盖掉。

## 4. 验证修复覆盖什么

将同一组探针分别链接修复前、修复后的生产 mixer，固定输入、回调计划和采样率。理想调度矩阵负责找算法性空洞；带人工生产延迟的墙钟模型负责检查余量与调度抖动，两者不能互相替代。

- 覆盖短块、长块、多种 callback、非整除组合及回调大小改变；比较 PCM 连续性、顺序、丢失/重复帧和队列上界。
- 同时放入完整背景通道与不足的语音通道，确认逐通道诊断能看到被全局最大值掩盖的缺帧。
- 对默认未配置路径、非阻塞提交、取消、停止、清空、释放/重新预约、短句末尾做回归；涉及 Android 的设备恢复另做生命周期检查。
- 留存测试命令、源文件哈希、测试产物与最终包对应关系。墙钟结果记录实际回调间隔和实际工作延迟；不要把标称 1 ms 等待解释成未经测量的固定 15.6 ms。

无设备探针不使用 XAudio2/AAudio 设备、guest 运行时、真实解码负载或游戏场景，不能代替人工听音、音画同步与真机恢复验证。用户保留自行试玩权时，继续完成离线回归和候选打包，并准确列出待用户验证项目。

## 5. 本案例的已知证据与适用边界

2026-10-16 最终对照将 Android 工程中的共享 AudioEngine 生产源码及修复前快照分别编成 Windows x64 无设备探针。每组顺序提交 120 个 448 帧 PCM 块，每次提交后施加 6 ms 人工生产工作；以下为该次运行包含起始阶段的缺失帧总数：

| 宿主回调帧数 | 修复前缺失帧 | 修复后缺失帧 | 修复后队列峰值 |
|---|---:|---:|---:|
| 192 | 0 | 0 | 1280 |
| 256 | 0 | 0 | 1472 |
| 512 | 768 | 0 | 1408 |
| 1024 | 7552 | 0 | 2496 |

修复后的四档均保持完整 PCM 样本顺序。1024 帧 guest 块配 512 帧回调在前后两版均无缺帧，队列峰值为 2048。默认未配置的 blocking 契约、大块 pacing、有界短块队列、有限尾音、无回调取消、重置后新音频、混音与逐通道统计的定向检查通过。

墙钟缺帧数受主机调度影响，会随运行波动；不能用这张表证明每次旧版都发生同样数量的缺口，也不能声称真实游戏解码耗时已测为 6 ms。这里证明的是受控生产延迟下的排队改善，理想调度下的非整除组合原本也可无缺帧。

另一个确定性诊断用完整 512 帧背景通道掩盖仅有 64 帧数据的语音通道：语音缺失 448 帧，全局旧指标仍报零。这里的缺口属于诊断统计，不能单独证明它就是用户现场断续的原因。

离线解码另检查了真实 `PSPBGM.BIN` 前三条 RIFF：生产 ATRAC 解码输出样本数均与 `fact` 声明一致，合计约 209.7 秒音频用时约 204.8 ms，单帧 P99 为 0.0665–0.0792 ms。它只覆盖这三条背景音乐，未验证 `PSPSND` 角色语音，不能据此声称全部对白素材或解码路径无误。当前证据没有支持重编码语音素材。

该策略已实现到 Windows、Android 及生成模板，以上生产源码定向回归已通过；仍未启动游戏、使用实际音频设备或验证 AAudio 驱动。实际 Windows 对白、红米 Turbo 3 的听音/音画同步与生命周期仍待验收。可以交付对应构建的候选修复，不能把它写为“真实游戏断续已确认消失”。
