# 高清资产、动态贴图与无损存储

本文件区分两个阶段：高清制作会改变画面像素，需要视觉验收；无损存储只改变已验收资产的编码，必须逐字节保持 RGBA。不要把“无损编码”宣传为“高清制作过程没有改变原画”。

## 先建立资产和运行时身份清单

- 对每个资源记录容器、偏移/扇区、原始长度、解码尺寸、像素格式、原始文件及解码像素 SHA-256。另记录实际运行时匹配键；不要用文件名或地址猜测纹理身份。
- 分类背景/CG、角色图集、字体、菜单/UI、效果、视频。记录完整资源数、唯一解码身份数、已处理数、跳过原因；入口画面截图不能证明全量覆盖。
- 先保留原画质可运行版本及已经验收的素材；新处理产物放入新目录。保留原尺寸/高清切换或等价回退，未知身份继续用原图。
- 本案例从 GRP 提取 2335 项，其中 1665 项为光栅资源、1514 个唯一解码身份。这些数字及地址只用于理解既有案例，不能当成新游戏的固定要求。

## 高清制作的正确粒度

背景经常由多个切片组成。先根据布局证据拼回完整画面，再统一放大、最后按同一倍率和原坐标切回；分别放大切片容易产生拼缝。本案例 274 组场景由两块 256×256 和两块 256×32 组成 512×288，再做 4 倍处理。其他布局必须重新确认。

角色/背景可试小样并比较批准效果。保留透明度和边缘覆盖；处理 RGB 时透明区边缘填充只属于制作步骤，不得偷偷混入无损存储阶段。确定性的缩放、恢复、打包脚本可以用于已有资产；需要新增或编辑图像时遵循当前环境的图像工具要求。只在风格已确认后批量制作，记录工具、模型版本、参数和许可。

UI、字库、名字和图标不能统一交给模型重新“画字”。优先保形缩放；只有字符映射、字形及字体许可明确时才重排字形。保留基线、字宽、边距、alpha 轮廓和颜色乘法。不要把 UTF 表中的可打印字符直接认作实际字形。

本案例全字库共 3700 槽，保留先前批准的 144 字；部分非 CJK 映射有重复/错位，采用保守轮廓恢复。运行时必须用完整原始字形单元的像素身份查找；相同原始位图无法区分语义，需统一输出并优先保留已批准版本。验证完整字库、旧小字库、空白、重复、未知字符回退，不能只验证几个常用汉字。

## 可变表情图集

游戏可能每帧把图集内的眼睛、嘴形区域复制到角色脸上，整张图的 hash 因此改变。固定 hash 替换无法覆盖这类图集。

1. 采集多个真实表情状态，定位基底及稳定锚点；证明变化是来源图集内的精确矩形复制。
2. 先匹配基底和未改锚点，再逐字节验证所有变化均能由已知复制矩形解释；限制矩形数、面积和尺寸。无法解释时保留原图，不能凭相似程度覆盖。
3. 高清层按相同比例复制同一源区域，保留透明度与坐标。已批准的整图替换应有明确优先级。
4. 使用真实捕获图集及故意篡改样本测试。检查脸/嘴接缝、半透明边缘、邻接采样和图集边界。GPU 双线性采样时的 padding/UV/边缘处理需由生产渲染路径证明。
5. 对基底缓存、高清缓存、GPU 纹理设预算；驱逐对象时不能释放当前 draw 仍引用的资源。磁盘文件变小不代表解码后内存和显存变小。

本案例采用 108 个基底，六组真实变化样本；严格复制匹配及边界处理的参数是游戏特定的，不要原样套用到未知游戏。

## 已有 RGTX 包的无损存储

附带脚本只接受已有原始包：每张纹理为 `RGTX` 四字节 magic、两个小端 uint32 宽高，共 12 字节头，随后为连续、非预乘 RGBA8。它不会从 ISO 提取资源、生成高清图或改动游戏运行时。

依赖 Python 3.11+ 和 Pillow；WebP 模式需要 Pillow 带 WebP 支持。示例在项目工作目录执行：

```powershell
python "<skill>/scripts/convert_rgba_pack.py" --source "work/hd-raw" --output "work/hd-stored-v1" --report "work/hd-stored-v1-audit.json" --codec best
```

`png` 比较原始 RGTX 与 PNG；`webp` 比较原始 RGTX 与无损 WebP；`best` 比较全部三种并取最小。平局保留先前候选。WebP 使用 `lossless=True, exact=True`，以保留 alpha=0 下的 RGB；不做预乘、颜色转换、量化、缩放或 alpha 清理。Pillow 对不透明 WebP 可能返回 RGB，比较前规范成 RGBA（补 alpha=255）。

脚本保持所有相对文件名及空目录，非纹理配置按原字节复制。每项报告包含源/存储大小与 SHA-256；纹理另含尺寸、源 RGBA 与解码 RGBA 字节数及 SHA-256、候选大小。解码字节必须完全一致，不能只比截图或只比可见像素。

脚本的通用输入上限为单边 16384、总像素 64 Mi；WebP 单边上限 16383。生产加载器可能更严格（本案例使用 8192 维度限制），交付前必须确认所有输出符合目标加载器及 GPU 限制，不能把通过本脚本当成尺寸兼容证明。`best` 对超出 WebP 单边限制的资产仍比较 PNG/RGTX。已压缩的 `.rgba`/`.legacy-rgba` 输入会被拒绝，始终从原始包开始。

输出与报告必须不存在。源和输出不可互相包含，报告必须在两个包以外；所有输入符号链接、Windows junction/reparse 路径均拒绝。失败保留部分输出但不生成成功报告，检查后使用新的输出/报告路径重试。不要在运行时同时编辑源包。脚本采取串行转换限制峰值内存；整包 WebP 编码时间可能较长。

## 运行时必须单独验收

本脚本只证明 Pillow 编码/解码和落盘像素相等，**不能证明生产解码器、GPU 渲染或整部游戏正常**。交付前继续完成：

- 保留原 RGTX 解码，按 magic 检测 PNG/WebP；若保留 `.rgba` 文件名，不能按扩展名决定编码。生产解码器先验证长度、尺寸、乘法溢出、分配上限与实际格式。拒绝截断、尾随非法数据、有损 WebP、动画以及不支持的 PNG 格式。
- 固定并记录编解码库版本及来源；静态链接时仍需带许可。Windows WIC 或 libwebp 必须输出非预乘 RGBA，禁止隐式色彩配置转换；如果依赖 COM，覆盖已有 STA apartment 情形。实际实现以目标平台为准。
- 通过**最终程序使用的生产加载器**遍历整包，逐字节比较原始 RGBA，验证所有配置及身份键未变。覆盖 alpha=0/1/127/255、隐藏 RGB、全不透明纹理、Unicode 路径、异常长度/维度和旧格式回退。
- 运行完整字体和真实可变表情/接缝夹具；用生产绘制计划及 GPU 路径验证透明混合、采样、上传、缓存生命周期。离屏夹具截图标明“离屏验证”，不能写成实际游玩截图。
- 测量总扫描时间、单图最大解码时间、峰值内存/显存、冷/热加载。若允许实际测试，再量场景切换和长时间运行；离线扫描不能证明无卡顿。用户已接管窗口时继续离线工作，不启动、切换、截图或关闭其游戏窗口。
- 只有最终候选包通过逐文件验收后才进入分发打包。变更素材或解码器后复用仍有效的证据，并补测受影响路径。

既有案例说明取舍：HD8.5 原始贴图包约 5.467 GB，经 PNG 存储到约 1.331 GB；HD8.6 再到约 0.994 GB，包含 1638 张 WebP、1 张 PNG、7 个原样配置。生产解码比较覆盖 1639 张纹理，约 5.466 GB RGBA 全部相同；同次配对全扫描 WebP 约 22.14 秒、PNG 约 35.24 秒，但 WebP 最慢单张约 1.94 秒。它是特定机器、素材与版本的记录，不是新项目的性能保证，也不代替实际场景测试。
