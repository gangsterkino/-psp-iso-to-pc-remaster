# Android 原生横屏与高清发布

用户明确选择 Android 时使用本分支。输入应是已辨认的 ISO、已有原生核心和对应运行时；先核实手机型号、系统版本、横竖屏与存档延续要求。复用会话已有答案。这里描述可复现的工程步骤，不提供游戏镜像、生成代码、素材或通用一键转换器。

## 1. 确定移植边界

- 盘点已有 CPU 重编译代码、HLE、文件系统、解码器、存档与宿主接口。Windows EXE 不能通过重新封装变成 Android APK；需要为 Android 编译并实现缺失的宿主后端。
- 要延续旧安卓存档时，先取得旧 APK 的 application ID、versionCode、签名证书指纹，确认原签名密钥可用，并核对存档路径、格式和新旧运行时兼容性。身份或密钥未确认仍可推进离线移植，但不能宣称可保留数据覆盖升级，也不把换签或卸载当成默认解法。
- 优先单独复制或建立 Android 分支，排除桌面构建、镜像、素材、存档、私钥与临时缓存；保留上一版可运行结果。记录游戏特定段地址、重定位、入口和补丁来源。
- 区分可复用的通用 C++ 与 Win32/D3D/XAudio、桌面对话框、路径和线程假设。确认 ARM64 的指针宽度、对齐、未定义行为与依赖支持；并非任何 PSP ISO 都适用这条路线。
- 分阶段交付：原画质最小运行 → 输入/声音/存档 → 高清替换与实际倍数渲染 → 安装升级 → 真机验收。模拟器方案是另一条路线，不能悄悄替换用户选择的原生移植。

## 2. 固定并验证工具链

从官方来源取得 SDK/NDK，保存下载 URL、版本、大小和公布的校验值；读取适用许可并保留第三方声明。优先局部工具目录，不必安装完整 Android Studio 或改系统 PATH。

2026-10-16 的已验证案例组合是 NDK r30 `30.0.16248370`、Build Tools `36.0.0`、SDK Platform 36、JDK 17、CMake、Ninja、Python 3.11+，目标 `arm64-v8a`、最低 API 26。这是复现记录；新项目应核实当前官方工具与目标手机兼容性，不把这些版本当成永久默认。

先编译一个使用实际依赖的 ARM64 共享库探针，确认工具链可运行。项目可用 Gradle，也可按以下次序调用官方工具；两者选择其一并保存可复现入口：

1. CMake 使用 NDK 的 `build/cmake/android.toolchain.cmake`，指定 ABI、最低 API、构建类型与 Ninja。生成 PIC 共享库；只有单个 `.so` 时可评估静态 libc++，跨库交换 C++ 对象时重新核对运行时方案。
2. `javac --release 8 -classpath <android.jar>` 编译 Java；不要把新 SDK 的 `android.jar` 当成 Java 8 bootclasspath。
3. 用 `java -cp <d8.jar> com.android.tools.r8.D8 --min-api <最低API>` 生成 DEX；aapt2 编译资源并链接 Manifest。
4. 加入 DEX、`lib/arm64-v8a/<库名>.so` 和已批准的 assets；检查 `extractNativeLibs` 与压缩策略一致。直接映射的 native 库必须不压缩并正确对齐。
5. 对未签名 APK 执行 `zipalign -P 16 -f 4`，再用 apksigner 签名；任何签名后的内容修改都要重新签名。

工具来源可从 [NDK 下载页](https://developer.android.com/ndk/downloads) 和 [Android Studio/命令行工具页](https://developer.android.com/studio) 核实。只下载完成当前构建所需的组件。

## 3. 实现 Android 宿主适配

- 将原生核心编译成 ARM64 `.so`，由 Java/JNI 或适合工程的 native Activity 入口启动。核对 JNI 方法名、参数、导出以及异常回传；不要在 UI 线程执行 guest 主循环或大文件导入。
- 独立渲染线程持有 EGL 上下文和 GLES 状态；正确获取/释放 `ANativeWindow`，处理 Surface 创建、销毁、重建和上下文失效。窗口变化后恢复尺寸、渲染目标和显示映射。
- 映射实际使用的绘制状态、纹理、CPU/GE 帧缓冲来源、目标别名、混合、深度和模板行为。用真实渲染路径测试，不以替代着色器或测试专用绘制器代替生产代码。
- 通用解码/混音接 AAudio 等 Android 输出。保留采样率、声道、阻塞写入的 guest 节奏；断开/停止要取消无回调时的等待，由回调之外的线程关闭并重开设备。不能以静音绕过同步问题。
- 系统存读档、确认和文字输入对话框通过 UI 线程桥接，明确返回值与取消语义。输入对话框期间阻止游戏按键穿透。

## 4. 横屏、触控与生命周期

- Manifest 声明所需横屏策略；保持游戏原比例，结合系统栏、刘海与手势安全区域安排两侧触控。不要把控件坐标直接当 guest 坐标。
- 多点触控按 pointer ID 管理；短按锁存至 guest 读取，松开、取消、失焦和暂停时清除输入。点击画面确认、返回与菜单的映射按实际游戏核实。
- 后台、失去音频焦点或没有 Surface 时暂停 guest 调度和声音；恢复时同时检查窗口与音频状态。只暂停渲染会让剧情/声音在后台继续前进。
- 退出要发布统一停止状态，唤醒 HLE 信号量、睡眠、音频等阻塞等待，回收线程后再释放 guest RAM。不可重入的单例运行时需设计明确的结束/重新启动路径。
- Activity 重建时串行处理上一轮取消、临时文件清理与新导入；避免旧 Activity 清理新任务正在写入的目录。存档位于稳定的应用私有路径，更新时不搬动或覆盖。

## 5. 接入高清，而不只放大最终画面

- 复用 PC 已验证的整图身份匹配 → 精确字格替换 → 动态表情重建及接缝处理；无可靠匹配时回退原图。字库映射和动态区域必须来自该游戏的证据。
- 保留 UI/字库样式、透明度、原图优先级和帧缓冲采样规则。高分素材与放大内部渲染是两件事，分别验证。
- 实际倍数应覆盖 FBO 尺寸、viewport、scissor、目标别名、纹理采样和最终呈现。480×272 的 4× 可见区域是 1920×1088；只有最后一步拉伸不算 4× 内部渲染。
- 2×/3× 可作为运行负载选项而保留全部高清素材；原画质模式明确关闭替换并使用 1×。这些选项不要偷换成对发行素材做有损压缩。
- 移动端无 PNG 解码器时，只转换不支持的条目为无损 WebP/RGTX，保留运行时文件名和配置。比较全部 straight RGBA，包括 alpha=0 的隐藏 RGB；同时用最终生产解码器验证，不只 Pillow 回读。
- 按实际解码尺寸计算预算：例中字库 5120×4640 约 90.6 MiB，108 张动态原图约 91 MiB，单张 2048² RGBA 为 16 MiB。压缩文件小不意味着运行内存小。
- 查询设备最大纹理尺寸；字库整页不一定需要整张上传 GPU。CPU 按需加载和 GPU LRU 分开限额，避免逐帧反复解码；报告缓存预算时说明它不是整个进程峰值。

## 6. 资源安装与可分发组合

按用户当前用途产出完整首次安装 APK、程序小 APK、独立高清 ZIP；可以只交付其需要的组合。小 APK 应复用同应用已有 ISO/高清包/存档，缺资源时通过系统文件选择器导入，不要求卸载旧版。

小包同样携带所需 ISO 身份和高清资源清单/版本。仅在已有数据与当前要求兼容时复用；资源改变就提供匹配的新包并验证后再启用高清，不能只凭“目录存在”或旧完成标记继续启动。资源不兼容时保留原有效包及存档，清楚提示所需资源；能否继续原画质由已验证的 ISO/核心兼容性决定。

在 skill 根目录使用随附的 [android_hd_pack.py](../scripts/android_hd_pack.py) 从干净素材 staging 生成 ZIP_STORED 和配套清单：

```text
python scripts/android_hd_pack.py build --source <素材staging> --archive <新hd-pack.zip> --manifest <新hd-manifest.json> --version my-game-hd-v1
python scripts/android_hd_pack.py verify --archive <hd-pack.zip> --manifest <hd-manifest.json> --source <素材staging>
```

输入需已整理完成，两个新输出都放在 staging 外；`verify` 的 `--source` 可选，用于再与原 staging 逐字节核对。此工具只负责资源 ZIP/清单，不转换 ISO、生成高清图、构建 APK、生成二进制差分更新或安装手机；Android 安装器和渲染适配仍须在目标工程实现并验证。

工具采用本案例安装器的受限格式：根相对路径仅 ASCII 字母、数字、`_-.` 与目录分隔 `/`，长度不超过 240；最多 4096 个文件、单文件 256 MiB、ZIP 3 GiB、展开 6 GiB。拒绝大小写冲突、保留名、链接/硬链接及 Windows reparse 路径；只存普通文件，不保留空目录。若既有素材键不符合约束，应协调修改安装器与打包器，不能悄悄改名破坏运行时匹配。两个输出不是跨文件事务；异常会清理本次临时产物，强制结束进程后检查残留并换新版本名重建。

- 全包可嵌入已授权的 ISO 与高清 ZIP。预压缩 WebP 的内层 ZIP 可用 `ZIP_STORED`；避免整个资源读进内存。APK 大小限制须按选用渠道和工具实测，案例主动采用小于 2 GiB 的兼容预算，不宣称这是所有渠道通用上限。
- 固定清单至少含 `version`、`archive_sha256`、`size`、`unpacked_bytes`，以及逐文件 `path/size/sha256`。只列入明确资产集合，不混入日志、生成器、源代码、存档或私钥。
- 流式复制 ISO/ZIP，同时核对总大小和 SHA-256；解包时限制文件数、单文件/总量、路径长度，并逐文件验证。拒绝越界、重复、路径冲突、额外/缺失文件及链接、设备等特殊 ZIP 条目。
- 先写独立 staging，全部通过后写完成标记并原子替换。已有包先移至备份；替换失败恢复，进程中断可恢复旧目录。清理只覆盖本工具的受控暂存路径，绝不触碰 ISO/存档。
- 安装期间的空间至少考虑已安装 APK/旧资源、下载文件、暂存 ZIP、新解压目录和余量；约 1 GB 的高清 ZIP 安装时还会产生约 1 GB 解压副本。每阶段检查可用空间，并给出失败重试入口。
- 取消应保留旧的有效包并清理本次暂存。一次成功后启动只检查必要就绪信息，避免每次启动重复复制近 GB 资源；更新清单版本时重新验证安装。

## 7. 签名、验证与真实完成范围

保持 application ID 与签名证书，递增 `versionCode`，是本流程直接侧载覆盖更新的必要条件；还需保证存档/资源格式兼容。签名密钥单独安全保存，不放源码、skill、公开仓库或交付包。卸载会删除应用内部存档，说明中应明确。签名及顺序参照 [Android 应用签名](https://developer.android.com/studio/publish/app-signing) 与 [zipalign](https://developer.android.com/tools/zipalign)；页大小兼容另查 [16 KB 支持指南](https://developer.android.com/guide/practices/page-sizes)，ZIP 对齐不能代替 ELF 与设备检查。

在最终源码和 APK 上记录以下证据，修改相关内容后重跑对应检查：

1. ARM64 编译/链接、JNI 导出和动态依赖正确；ELF LOAD 对齐支持 16 KiB，APK `zipalign -c -P 16 4` 及 apksigner 验证通过。对齐 ZIP 不会自动修复 ELF。
2. APK 全量 CRC、大小、SHA-256、包名/版本/ABI；完整包与小包的程序内容一致，内嵌 ISO/高清 ZIP 哈希与输入清单一致，签名证书与旧版一致。
3. 全素材生产解码像素一致，已批准字格/未知字格/真实动态表情回归通过。实际 Renderer 的离屏 FBO 尺寸、裁剪、别名和采样读回通过；着色器测试与同一批渲染测试不能重复计数。
4. 安装器覆盖正确安装升级、错误哈希、截断、额外/缺失/重复文件、路径/配额/类型、取消及备份恢复；使用真实完整资源包执行安装、就绪检查和独立重哈希，验证存档/ISO 未变。小型虚构夹具不能替代真实包验证。
5. 真机分别验证安装、标题/剧情、高清切换、触控、声音、存读档、后台/Surface/音频焦点恢复、长时间内存/温度/帧率。没有连接设备就保留这些待验项，不能把 Windows ANGLE 或 JVM 成功说成手机可玩。

当前案例 A0.2 已有 ARM64 包、同 PC 像素的高清资产、默认实际 4× 与安装升级证据；完整资源安装曾在 64 MiB JVM 堆限制下通过。它仍没有 Android 真机游玩证据，视频解码关闭，AUTO/SKIP 控件未接入，部分 GLES 状态仍有限制。这些缺口必须如实保留到实现并验收，不因生成了 APK 就消失。

交付记录包路径、体积、哈希、首次安装/覆盖更新步骤、资源和存档位置、设备测试范围、缺口与下一步。仅编写/更新本 skill 不授权下载 ISO、执行游戏、上传 APK 或公开任何原作内容；外部发布仍按用户明确授权范围执行。
